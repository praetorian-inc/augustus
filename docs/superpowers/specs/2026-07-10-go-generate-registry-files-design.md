# Design: `go generate` for Augustus registry files (LAB-1248)

## Problem

Augustus wires capability registration through five hand-maintained blank-import
files under `pkg/register/`:

| Capability | File |
|---|---|
| Probes | `pkg/register/probes/probes.go` |
| Detectors | `pkg/register/detectors/detectors.go` |
| Generators | `pkg/register/generators/generators.go` |
| Buffs | `pkg/register/buffs/buffs.go` |
| Harnesses | `pkg/register/harnesses/harnesses.go` |

aggregated by `pkg/register/register.go`, which is pulled in by
`cmd/augustus/main.go`. Each `internal/<type>/<pkg>` package has an `init()`
that calls `<type>.Register(...)`; the register files exist solely to force
those imports so the `init()` side effects run.

These files must be edited by hand whenever a capability package is added. This
already drifted: `internal/detectors/poetry` calls
`detectors.Register("poetry.HarmJudge", ...)` but is **missing** from
`pkg/register/detectors/detectors.go`, so that detector is not registered in
built binaries.

The task (LAB-1248) is to generate these files with `go generate`, eliminating
the manual step and the drift.

## Goals

- Generate all five register files from the contents of `internal/<type>/`.
- Drive it with `go generate` so `go generate ./...` regenerates everything.
- Add a CI drift check so a PR that adds a capability without regenerating fails.
- Fix the `detectors/poetry` drift as a natural consequence of regeneration.

## Non-goals

- No change to the registration mechanism itself (`init()` + `Register(...)`).
- No change to `pkg/register/register.go` (the aggregator) — it is stable and
  lists the five per-type packages, which are not expected to change.
- No unrelated refactoring.

## Design

### 1. Generator tool — `tools/genregister/main.go`

A small standalone Go program (lives beside the existing `tools/multimodal-assets/`).

**Module-root discovery.** Walk up from the working directory to find `go.mod`,
so the tool resolves the same absolute paths regardless of where
`go generate` invokes it.

**Type table.** One entry per capability drives the whole run:

| type | scan dir | register selector | output file | package name |
|---|---|---|---|---|
| probes | `internal/probes` | `probes.Register` | `pkg/register/probes/probes.go` | `probes` |
| detectors | `internal/detectors` | `detectors.Register` | `pkg/register/detectors/detectors.go` | `detectors` |
| generators | `internal/generators` | `generators.Register` | `pkg/register/generators/generators.go` | `generators` |
| buffs | `internal/buffs` | `buffs.Register` | `pkg/register/buffs/buffs.go` | `buffs` |
| harnesses | `internal/harnesses` | `harnesses.Register` | `pkg/register/harnesses/harnesses.go` | `harnesses` |

**Detection via `go/ast`.** For each immediate subdirectory of the scan dir,
parse its `.go` files (skipping `_test.go`) and include the package **iff** some
file contains a call expression whose selector matches `<pkg>.Register` (e.g.
`probes.Register(...)`). This:

- excludes helper packages with no registration (`internal/probes/topic`,
  `internal/generators/{googleai,openaicompat,wsutil}`),
- includes `internal/detectors/poetry` (currently missing), and
- is robust to future additions/removals.

The import path for an included package is
`github.com/praetorian-inc/augustus/<scan dir>/<subdir>`.

**Emission.** For each type, build the file body:

- `// Code generated by tools/genregister; DO NOT EDIT.` header.
- The existing package doc comment preserved above `package <name>`.
- A single `import (...)` block of blank imports, one per included package,
  sorted by import path.

Run the assembled source through `go/format.Source` so output is
gofmt/gofumpt-clean and matches what `golangci-lint fmt` enforces. Write only if
content changed (avoids spurious mtime churn).

### 2. Directive — `pkg/register/generate.go`

A dedicated file holding the single directive:

```go
//go:generate go run ../../tools/genregister
package register
```

`go generate ./...` discovers it. The tool self-locates the module root, so the
exact relative path in the directive is not load-bearing for path resolution —
it only needs to point `go run` at the tool package.

### 3. Makefile targets

Mirror the existing `multimodal-assets-verify` pattern:

```make
generate:
	go generate ./...

generate-check:
	go generate ./...
	git diff --exit-code -- pkg/register
```

`generate-check` regenerates and fails if the working tree differs, catching a
PR that added a capability without regenerating.

### 4. CI wiring

CI delegates entirely to the centralized `public-workflows/go-ci.yml`, which
runs `go test ./...` and exposes no step hook for a `make` target, and the repo
convention avoids bespoke jobs pinning third-party action SHAs. So drift
enforcement is implemented as a **Go drift-guard test**
(`TestRegisterFilesUpToDate`) that regenerates in-memory and compares against the
committed `pkg/register/<type>/*.go` files. It runs under the existing CI test
job with no workflow changes, and locally via `make test`. The
`make generate-check` target remains for explicit local verification.

## Testing

- **Unit test** for the detection function: a fixture directory tree with (a) a
  package that calls `<type>.Register(`, (b) a helper package that does not, and
  (c) a package that calls some other `Register` — asserts only (a) is included.
- **Golden/idempotency test**: running the generator twice produces identical
  output (second run is a no-op diff).
- **Verification** (manual, before commit): run `go generate ./...`; confirm the
  only diff is the `detectors/poetry` addition; then `make build` and
  `make test` stay green, and `golangci-lint fmt ./...` reports no changes.

## Outcome

After this change, adding a capability requires only creating the package with
its `init()`/`Register(...)`; `go generate ./...` (or `make generate`) updates
the register files, and CI enforces it. The `detectors/poetry` detector becomes
registered.
